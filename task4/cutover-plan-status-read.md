# Cutover plan: чтение статусов заказа из сервиса статусов

Oct 1, 2026 · @Alexander Fedorov

## 1. Цель и границы переключения

Переключение переводит чтение статуса и истории заказа с монолита на сервис статусов, чтобы покупатель, поддержка и маркетплейсы видели один и тот же статус с понятной причиной отклонения. Это первое переключение промышленного трафика в программе (этап 1, месяц 6); оно также проверяет полноту потока событий заказа, на котором строятся следующие этапы.

| № | В границах переключения | Вне границ |
| --- | --- | --- |
| 1 | Чтение статуса и истории заказа из личного кабинета и мобильного приложения | Создание и изменение заказа — остаются в монолите |
| 2 | Карточка и история заказа в административных инструментах (чтение) | Ручная смена статуса — остаётся прежней до этапа 2 |
| 3 | Запросы статуса маркетплейсами через Order API (контракт не меняется) | Передача статусов в маркетплейсы по инициативе платформы — без изменений |
| 4 | Маршруты чтения в API Gateway | Уведомления — отдельное переключение этапа 2 |

Источником правды о состоянии заказа остаётся монолит и Oracle; сервис статусов — проекция для чтения. Поэтому откат не требует переноса данных обратно и выполняется маршрутом в API Gateway.

## 2. Условия запуска

Переключение начинается, только если выполнены все условия ниже; решение go/no-go принимает руководитель переключения на совещании за день до старта и повторно в день старта.

- [ ] Сервис статусов отработал в теневом режиме не менее двух недель, включая одну маркетинговую кампанию.
- [ ] Доля расхождений статуса в теневом сравнении ниже согласованного порога в течение последних семи дней; каждое оставшееся расхождение объяснено.
- [ ] Задержка проекции относительно изменения в Oracle (p99) не превышает допустимой задержки статуса, согласованной с руководителем заказов.
- [ ] Сверка событий с Oracle без необъяснённых расхождений две недели подряд; CDC покрывает смены статуса из batch, админки и PL/SQL.
- [ ] Нагрузочный тест сервиса статусов и API Gateway на пиковом профиле этапа 0 с запасом пройден.
- [ ] Панели мониторинга и оповещения из раздела 6 настроены и проверены.
- [ ] Rollback отрепетирован на предпромышленной среде; время возврата маршрута измерено.
- [ ] Режим чтения из монолита полностью работоспособен и не изменялся в период теневого режима.
- [ ] Поддержка обучена работе с новой карточкой заказа и справочником причин; скрипты ответов обновлены.
- [ ] Дата не попадает на сезонный пик, крупную кампанию или релиз монолита; на время переключения и два дня после объявлен запрет на релизы затронутых компонентов.

Значения порогов (доля расхождений, допустимая задержка, запас по нагрузке) фиксируются по итогам измерений этапа 0 и теневого режима; сейчас входных данных для них нет.

## 3. Роли и ответственность

На время переключения работает общий канал связи; решение об откате может принять любой из двух руководителей без согласования с остальными.

| № | Роль | Кто | Ответственность |
| --- | --- | --- | --- |
| 1 | Руководитель переключения | Архитектор решения | Решение go/no-go, переход между шагами, решение об откате, закрытие переключения |
| 2 | Технический руководитель | Технический лидер ядра | Состояние монолита, outbox и CDC; решение об откате |
| 3 | Владелец сервиса статусов | Команда сервиса статусов | Состояние сервиса и проекции, дозагрузка событий, исправление расхождений |
| 4 | Инженер эксплуатации | Инфраструктура и эксплуатация | Изменение маршрутов в API Gateway, мониторинг инфраструктуры, выполнение отката |
| 5 | Наблюдающий за метриками | Инженер наблюдаемости | Панели и пороги, доклад о состоянии на каждой контрольной точке |
| 6 | Представитель поддержки | Тимлид смены поддержки | Ручная проверка заказов, сигнал о росте обращений или жалобах на статус |
| 7 | Представитель бизнеса | Руководитель команды заказов | Приёмка результата, решение по спорным расхождениям смысла статуса |
| 8 | Контакт по маркетплейсам | Команда партнёрских интеграций | Проверка ответов маркетплейсам, связь с партнёрами при ошибках |

## 4. Состояние данных и сравнение контуров

Новый контур получает промышленный трафик только тогда, когда его ответы совпадают с монолитом; сравнение продолжается и после переключения.

### 4.1. Подготовка данных

1. Начальная загрузка: проекция строится из снимка Oracle для активных заказов и заказов за период, доступный покупателю в личном кабинете; снимок и позиция журнала изменений фиксируются одновременно.
2. Догрузка: события и CDC применяются с зафиксированной позиции; события с версией заказа не выше уже применённой отбрасываются.
3. Старые заказы, не попавшие в загрузку, обслуживаются монолитом: API Gateway направляет туда запрос, если сервис статусов отвечает «заказ не найден».
4. Сопоставление статусов: каждый внутренний статус монолита, включая особые статусы двух маркетплейсов и логистического партнёра, сопоставлен клиентскому статусу; неизвестный статус не скрывается, а фиксируется как расхождение.
5. Для маркетплейсов ответ формируется в прежнем формате и с прежними значениями статусов; новые клиентские статусы им не передаются.

### 4.2. Теневое сравнение

API Gateway дублирует запрос чтения в сервис статусов; клиенту возвращается ответ монолита, а пара ответов записывается для сравнения. Режим работает до переключения и в обратную сторону — весь период наблюдения после него.

| № | Что сравнивается | Как считается расхождение |
| --- | --- | --- |
| 1 | Внутренний статус заказа | Не совпадает по истечении допустимой задержки с момента изменения |
| 2 | Клиентский статус | Не соответствует правилу сопоставления для внутреннего статуса |
| 3 | Ответ маркетплейсу | Любое отличие поля или формата |
| 4 | Срок доставки и сумма в карточке | Любое отличие после допустимой задержки |
| 5 | Полнота истории | Изменение статуса в Oracle без записи в истории сервиса |

Расхождения разбираются ежедневно и классифицируются: задержка, пропущенное событие, ошибка сопоставления, ошибка монолита. Расхождение, в котором прав новый контур (например, устаревшая витрина статусов монолита), фиксируется отдельно и не блокирует переключение, если с ним согласен представитель бизнеса.

## 5. Пошаговый сценарий

Переключение идёт от внутренних пользователей к покупателям и только потом к маркетплейсам, доля трафика растёт после каждой контрольной точки. Д — день переключения; переключения выполняются в рабочие часы вне суточного пика заказов, когда на месте все роли. При нарушении любого порога из раздела 6 выполняется rollback.

| № | Когда | Действие | Ответственный | Контрольная точка для перехода дальше |
| --- | --- | --- | --- | --- |
| 1 | Д–1 | Совещание go/no-go по чек-листу раздела 2; уведомление затронутых команд и поддержки | Руководитель переключения | Все пункты чек-листа выполнены |
| 2 | Д, старт | Повторная проверка панелей: задержка проекции, расхождения за последние сутки, состояние брокера и CDC; фиксация базовых значений метрик | Наблюдающий за метриками | Показатели в норме, решение go подтверждено |
| 3 | Д | Чтение карточки и истории в административных инструментах переключается на сервис статусов для смены поддержки | Инженер эксплуатации | 4 часа работы; тимлид поддержки подтверждает совпадение на выборке сложных заказов (маркетплейс, частичная отмена, ручная проверка) |
| 4 | Д | Чтение статуса в личном кабинете и приложении: 5% покупателей (стабильное распределение по идентификатору покупателя) | Инженер эксплуатации | 4 часа в пределах порогов; нет роста обращений о статусе |
| 5 | Д+1 | Доля покупателей увеличивается до 25% | Инженер эксплуатации | Рабочий день в пределах порогов; ежедневная сверка без новых классов расхождений |
| 6 | Д+2 | Доля покупателей увеличивается до 50% | Инженер эксплуатации | Рабочий день в пределах порогов; нагрузка на сервис статусов в пределах запаса |
| 7 | Д+3 | Доля покупателей увеличивается до 100% | Инженер эксплуатации | Два рабочих дня в пределах порогов, в том числе суточный пик заказов |
| 8 | Д+5 | Запросы статуса от одного маркетплейса с наименьшим объёмом заказов | Контакт по маркетплейсам | День без ошибок формата и расхождений с ответами монолита; нет сигналов от партнёра |
| 9 | Д+6 | Запросы статуса остальных маркетплейсов по одному | Контакт по маркетплейсам | Каждый маркетплейс — день без ошибок перед следующим |
| 10 | Д+6 … Д+34 | Период наблюдения: теневое сравнение в обратную сторону, ежедневная сверка, чтение из монолита сохраняется как резерв | Владелец сервиса статусов | Четыре недели или один пиковый период в пределах порогов |
| 11 | После наблюдения | Закрытие переключения (раздел 9) | Руководитель переключения | Приёмка представителем бизнеса |

На шагах 3–9 данные не переносятся и не изменяются: меняется только маршрут чтения в API Gateway. Оба источника остаются актуальными всё время.

## 6. Наблюдаемость и пороги

Все метрики собраны на одной панели переключения и разделены по маршруту (монолит или сервис статусов), чтобы новый контур сравнивался со старым на одном трафике. Каждый запрос несёт сквозной идентификатор заказа и признак маршрута.

| № | Метрика | Порог для остановки | Порог для отката |
| --- | --- | --- | --- |
| 1 | Доля ошибок ответа сервиса статусов | Выше доли ошибок монолита на том же трафике | Вдвое выше доли ошибок монолита или рост 15 минут подряд |
| 2 | p95/p99 времени ответа чтения статуса | Хуже базового значения монолита | Хуже базового значения более 15 минут |
| 3 | Задержка проекции относительно Oracle (p99) | Близко к допустимой задержке статуса | Превышает допустимую задержку |
| 4 | Отставание потребителя событий и CDC | Растёт более 10 минут | Не сокращается после вмешательства |
| 5 | Доля расхождений в теневом сравнении | Выше уровня теневого режима | Появился новый класс расхождений или доля выше согласованного порога |
| 6 | Ошибки формата в ответах маркетплейсам | Любая ошибка | Любая повторяющаяся ошибка или сигнал от партнёра |
| 7 | Обращения в поддержку о статусе заказа | Рост относительно того же дня недели | Рост, подтверждённый тимлидом поддержки как связанный с переключением |
| 8 | Время оформления заказа и нагрузка на Oracle | Любое ухудшение относительно базового | Ухудшение, связанное с переключением |

При пороге остановки доля трафика не увеличивается, пока причина не найдена. При пороге отката rollback выполняется сразу, анализ — после. Оповещения по порогам отката идут руководителю переключения, техническому руководителю и инженеру эксплуатации. Точные значения порогов определяются по базовым метрикам этапа 0 и фиксируются на совещании go/no-go.

## 7. Проверки после переключения

Проверки выполняются после каждого шага сценария и в конце каждого дня периода наблюдения.

| № | Проверка | Как выполняется | Кто | Ожидаемый результат |
| --- | --- | --- | --- | --- |
| 1 | Контрольные заказы | Заранее подготовленный набор заказов в разных состояниях: обычный, с маркетплейса, с частичной отменой, на ручной проверке, с ожиданием оплаты и доставки | Представитель поддержки | Статус, история и причина отклонения совпадают с монолитом |
| 2 | Новое изменение доходит до клиента | Тестовый заказ проводится по статусам; статус меняется из кода, из batch-процедуры и через админку | Владелец сервиса статусов | Статус в личном кабинете обновляется в пределах допустимой задержки для всех трёх источников изменения |
| 3 | Сквозная трассировка | По номеру контрольного заказа прослеживается путь: изменение в монолите, событие, проекция, ответ API Gateway | Наблюдающий за метриками | Все звенья видны, задержки измерены |
| 4 | Сверка с Oracle | Полная сверка статусов активных заказов в проекции и в Oracle раз в сутки | Владелец сервиса статусов | Необъяснённых расхождений нет |
| 5 | Ответы маркетплейсам | Сравнение ответов нового и старого контура по теневому журналу, проверка ошибок интеграции | Контакт по маркетплейсам | Ответы идентичны по формату и значениям |
| 6 | Без влияния на оформление | Сравнение p95/p99 оформления и нагрузки на Oracle с базовыми значениями | Технический руководитель | Не хуже базового; нагрузка на Oracle от чтения статусов снизилась |
| 7 | Работа поддержки | Опрос смены, анализ обращений о статусе | Представитель поддержки | Операторы отвечают без перехода в соседние интерфейсы; число обращений не выросло |

## 8. Rollback-сценарий

Откат — это возврат маршрута чтения в API Gateway на монолит; данные не восстанавливаются, потому что источник правды всё время остаётся в Oracle. Откат возможен на любом шаге до закрытия переключения; время возврата маршрута измеряется на репетиции.

Основания для отката:

- любой порог отката из раздела 6;
- недоступность сервиса статусов, брокера или CDC, которую не удаётся устранить за 15 минут;
- решение руководителя переключения или технического руководителя по любой другой причине, в том числе по сигналу поддержки или маркетплейса.

| № | Действие | Ответственный |
| --- | --- | --- |
| 1 | Объявить откат в канале переключения и зафиксировать время и причину | Руководитель переключения |
| 2 | Вернуть маршрут чтения на монолит для всех потребителей: маркетплейсы, покупатели, админка | Инженер эксплуатации |
| 3 | Убедиться, что весь трафик чтения идёт в монолит, а доля ошибок и время ответа вернулись к базовым | Наблюдающий за метриками |
| 4 | Проверить контрольные заказы в личном кабинете и админке; проверить ответы маркетплейсам | Представитель поддержки, контакт по маркетплейсам |
| 5 | Сохранить журналы, трассы и теневые пары ответов за период инцидента | Владелец сервиса статусов |
| 6 | Сервис статусов продолжает получать события и работать в теневом режиме; при повреждении проекции она перестраивается из снимка Oracle | Владелец сервиса статусов |
| 7 | Разобрать причину в течение двух рабочих дней, обновить чек-лист запуска и назначить новую дату; повторный старт — с шага 1 сценария | Руководитель переключения |

Если часть покупателей или маркетплейсов получила неверный статус, по журналу теневого сравнения составляется список затронутых заказов; поддержка и команда интеграций решают, нужно ли повторно уведомить покупателей или партнёров.

## 9. Завершение переключения и коммуникации

Переключение считается завершённым, когда период наблюдения прошёл в пределах порогов и представитель бизнеса принял результат.

После завершения:

- [ ] Теневое сравнение в обратную сторону отключено; ежедневная сверка с Oracle сохраняется как постоянная проверка.
- [ ] Чтение статуса из монолита остаётся доступным как аварийный маршрут до конца этапа 2; его удаление планируется отдельным решением.
- [ ] Устаревшая витрина статусов монолита внесена в реестр объектов на вывод после проверки других потребителей.
- [ ] Отчёт о переключении: фактические метрики, расхождения и их причины, изменение числа внутренних касаний на обращение, уроки для следующих переключений.
- [ ] Решение зафиксировано в ADR; шаблон этого плана обновлён для переключений этапа 2.

Коммуникации:

| № | Кому | Когда | Что |
| --- | --- | --- | --- |
| 1 | Команды ядра, интеграций, эксплуатации | За неделю и за день до старта | Дата, сценарий, запрет на релизы затронутых компонентов |
| 2 | Клиентская поддержка | За неделю до старта и в каждый день сценария | Что меняется в карточке, куда сообщать о расхождениях |
| 3 | Спонсор и руководитель команды заказов | После каждой контрольной точки и при откате | Состояние, доля трафика, инциденты |
| 4 | Маркетплейсы | Не требуется, контракт не меняется; сообщение только при ошибках, затронувших партнёра | Период и список затронутых заказов |
| 5 | Покупатели | Не требуется | — |
